# Контекст проекта Depersonalization

## Цель

Разработать локальный сервис обезличивания персональных данных для использования в workflow n8n. Основной сценарий: обработка резюме и других документов до передачи текста во внешний OpenAI/AI API.

Исходное описание находится в документе:

`G:\Мой диск\ИИ\Privacy Filter OpenAI(обезличивание данных).docx`

Документ изучен 2026-07-20. Оригинал не изменялся и в репозиторий не копировался. В нём предложена цепочка `n8n -> HTTP API -> opf CLI -> redacted_text -> OpenAI`. Общая идея принята, но запуск CLI-процесса на каждый запрос решено заменить прямым Python API.

## Текущее состояние

- Реализация сервиса ещё не создана.
- В репозитории пока находится только минимальный `README.md` и этот файл контекста.
- Следующая задача: собрать рабочий MVP, тесты и пример интеграции с n8n.
- Не коммитить модельные веса, токены, исходные резюме или иные персональные данные.

## Выбранная архитектура

Под «одним контейнером» понимается один отдельный контейнер Privacy Filter API, размещённый рядом с контейнером n8n. Не объединять n8n и Privacy Filter в один контейнер.

Поток данных:

1. n8n получает DOCX/PDF или другой документ.
2. n8n извлекает текст узлом `Extract From File` или эквивалентным узлом.
3. n8n отправляет текст во внутренний сервис `http://privacy-filter:8000/v1/redact`.
4. Сервис запускает OpenAI Privacy Filter и правила для российских идентификаторов.
5. Только `redacted_text` передаётся следующему AI-узлу.
6. При остаточных признаках PII workflow останавливается или направляется на ручную проверку.

Контейнеры должны находиться в одной внутренней Docker-сети. Privacy Filter не должен публиковать порт в интернет или на интерфейсы хоста; в Compose использовать `expose`, а не `ports`.

## Модель и способ вызова

Использовать официальный репозиторий OpenAI:

- Репозиторий: https://github.com/openai/privacy-filter
- Пакет: `opf`
- Лицензия: Apache 2.0
- Модель: 1.5B параметров всего, около 50M активных параметров
- Основной язык модели: английский; качество на русском и других non-Latin текстах может снижаться.

Критическое решение: не использовать `subprocess.run(["opf", ...])` на каждый HTTP-запрос. В приложении создать один экземпляр публичного класса `opf.OPF` при старте:

```python
from opf import OPF

redactor = OPF(
    model="/models/privacy-filter",
    device="cpu",
    output_mode="typed",
)
```

Модель должна загружаться один раз и повторно использоваться. Запускать один Uvicorn worker и ограничивать одновременный inference через `Semaphore` или очередь. Для CPU на VPS 4 vCPU / 8 GB начинать с concurrency=1. На общем сервере с n8n и PostgreSQL 8 GB может быть тесно; перед production провести нагрузочный тест, предпочтительная конфигурация — 16 GB RAM.

Поскольку у upstream-репозитория нет стабильных releases, при сборке фиксировать конкретный commit SHA. Ревизию модельных весов также фиксировать. Модель хранить в named volume `/models`, если её размер не позволяет удобно включить веса в образ.

## API-контракт MVP

Endpoints:

- `GET /health/live` — процесс запущен.
- `GET /health/ready` — модель полностью загружена и сервис готов к inference.
- `POST /v1/redact` — обезличивание одного текста.
- `POST /v1/redact/batch` — не включать в первый MVP; добавить после измерения памяти и производительности.
- Swagger `/docs` отключить в production или оставить доступным только во внутренней сети.

Пример запроса:

```json
{
  "text": "Иван Иванов, телефон +7 999 123-45-67",
  "mode": "typed",
  "policy": "ru_resume"
}
```

Безопасный production-ответ:

```json
{
  "schema_version": 1,
  "redacted_text": "<PRIVATE_PERSON>, телефон <PRIVATE_PHONE>",
  "summary": {
    "span_count": 2,
    "by_label": {
      "private_person": 1,
      "private_phone": 1
    },
    "pii_check_passed": true
  }
}
```

Официальный OPF-результат содержит исходный `text` и `detected_spans[*].text`. Не возвращать эти поля по умолчанию, иначе исходные персональные данные попадут в историю выполнения n8n. Полный диагностический результат разрешать только в явно включённом debug-режиме, который нельзя использовать в production.

## Правила для русского языка

OPF использовать как основной контекстный детектор, но объединять его интервалы с детерминированными правилами, работающими на исходном тексте. Затем разрешать пересечения, выполнять замену единым проходом и повторно сканировать результат.

Профиль `ru_resume` должен проверять минимум:

- email и URL;
- российские номера телефонов;
- Telegram username и ссылки;
- ИНН (10 или 12 цифр);
- СНИЛС;
- серию и номер паспорта;
- банковские карты с проверкой Luhn;
- расчётные, лицевые и другие номера счетов;
- даты рождения по контексту.

Корректный базовый шаблон ИНН:

```regex
\b(?:\d{10}|\d{12})\b
```

Не использовать шаблон `\b\d{10}|\d{12}\b`: из-за приоритета alternation границы слова применяются только к отдельным веткам.

Результаты OPF и regex не должны заменять друг друга. Следует объединять интервалы и отдавать приоритет более специфичному правилу. Все правила покрыть unit-тестами, включая ложные срабатывания.

## Безопасность и приватность

- Сервис доступен только во внутренней Docker-сети.
- Аутентификация Bearer token остаётся дополнительным уровнем защиты.
- Токен передавать через Docker secret или переменную с суффиксом `_FILE`, не хранить в Compose и репозитории.
- Не логировать тело запроса, исходный текст, найденные фрагменты, Authorization header и текст исключений upstream.
- Не включать исходный текст в HTTP-ошибки.
- Установить ограничение размера запроса, таймаут, ограниченную очередь и ответ `429` при перегрузке.
- Использовать `read_only: true`, `tmpfs: /tmp`, `cap_drop: [ALL]` и `no-new-privileges:true`, если зависимости это допускают.
- Временные файлы удалять гарантированно; для текстового API они обычно не нужны.
- Не утверждать, что результат является гарантированной анонимизацией или обеспечивает compliance. Privacy Filter — один из слоёв privacy-by-design.
- Для HR и других чувствительных сценариев предусмотреть ручную проверку и тестирование на собственном корпусе.

## Настройки n8n

n8n по умолчанию сохраняет данные успешных и ошибочных выполнений. Для workflow с персональными данными отключить сохранение execution data на уровне выделенного экземпляра или самого workflow. Для отдельного n8n-инстанса рекомендуемые переменные:

```yaml
environment:
  EXECUTIONS_DATA_SAVE_ON_SUCCESS: none
  EXECUTIONS_DATA_SAVE_ON_ERROR: none
  EXECUTIONS_DATA_SAVE_MANUAL_EXECUTIONS: "false"
  EXECUTIONS_DATA_SAVE_ON_PROGRESS: "false"
```

Если существующий n8n обслуживает другие workflow и их историю необходимо сохранять, не менять глобальные настройки без согласования: использовать настройки конкретного workflow или отдельный n8n-инстанс для чувствительных данных.

В `HTTP Request` node использовать credential для Bearer token, а не вставлять секрет непосредственно в workflow. URL внутри общей сети: `http://privacy-filter:8000/v1/redact`.

## Обработка файлов

MVP принимает текст, а не бинарные DOCX/PDF. Извлечение текста остаётся ответственностью n8n. Это уменьшает образ и не требует LibreOffice, OCR и набора парсеров документов.

Если потребуется возвращать обезличенный DOCX/PDF с сохранением оформления, считать это отдельным этапом проекта. Нужно будет обрабатывать:

- основной текст и таблицы;
- колонтитулы, сноски и комментарии;
- свойства и метаданные файла;
- текст внутри изображений через OCR;
- координатное закрытие текста в PDF;
- проверку невозможности восстановления скрытого содержимого.

Обезличивание извлечённого текста само по себе не изменяет исходный документ.

## Критерии готовности MVP

- Модель загружается один раз при старте.
- `/health/ready` становится успешным только после загрузки модели.
- API не возвращает и не логирует исходный текст.
- Bearer token проверяется constant-time сравнением.
- Контейнер не имеет опубликованного внешнего порта.
- Поддерживаются OPF и профиль `ru_resume`.
- Повторная проверка не находит покрываемые правилами PII в `redacted_text`.
- Есть тесты российских форматов и API-ошибок.
- Есть интеграционный пример HTTP Request node для n8n.
- Проведён тест на целевом VPS: cold start, время обработки, память и очередь.
- Подготовлен тестовый корпус русскоязычных резюме без реальных персональных данных и зафиксированы precision/recall по классам.
